## What it protects against

The thing this exists to prevent is a credential **outliving its usefulness in a
place nobody is looking at**: a settings file copied into a backup, committed to
a repository, or pasted into an issue.

| | Credential in `openclaw.json` | Credential in a vault, resolved here |
| --- | --- | --- |
| In backups | Yes, in plain text | No |
| In a repository if committed | Yes | Only a name |
| Readable by any process running as you | Yes, from the file, forever | Yes, but only by asking the vault |
| Read is recorded | No | Yes, `pass-cli agent monitor` |
| Rotation | Edit every file that has it | Edit the vault item |
| Revocation | Change the credential everywhere | Revoke one agent token |

## What is on disk

Two things, and neither is a credential for the services you use:

<ResponseField name="openclaw-secret-map.json" type="mode 0600">
  Names and vault locations. Reading it tells you that a Context7 key exists and
  which vault item holds it. It does not tell you the key.
</ResponseField>

<ResponseField name="openclaw-agent-pat" type="mode 0600, optional">
  The agent token. **This is the root of the whole arrangement.** Anything that
  can read it can read that vault. Absent when the token is supplied through
  `OPENCLAW_PROTONPASS_AGENT_TOKEN` instead.
</ResponseField>

Both live in a directory created at mode `0700`, or, on Windows, with
inherited permissions dropped and full control granted to one account,
because `chmod` does nothing there.

### Choosing between the file and the variable

Neither is strictly safer; they fail differently, so pick for the host.

| | A file | An environment variable |
| --- | --- | --- |
| Readable by other accounts | No, mode `0600` | No |
| Readable by root or an administrator | Yes | Yes |
| Visible in `/proc/<pid>/environ` | No | Yes, to the same user and root |
| Ends up in a filesystem backup or image | Yes | No |
| Ends up in a platform's stored configuration | No | Yes, wherever that platform keeps it |
| Survives a rebuild of the machine | No | Yes, if the platform holds it |

A workstation is better served by the file: it is not visible to anything
inspecting the process, and the disk is already the thing being protected. A
container or a managed host is better served by the variable, because the
platform already has somewhere to keep a secret, and a token written into an
ephemeral filesystem during provisioning has to be written again on every
rebuild.

<Warning>
If you use the variable, check what your platform does with it. Some log the
environment of a failed start, some show it in a web console, and some copy it
into a build cache. That exposure is the platform's, not this project's, and
it is the one thing the file genuinely avoids.
</Warning>

## Design decisions that are security decisions

<AccordionGroup>
<Accordion title="The token is never a command-line argument">

`pass-cli` accepts the token either as `--personal-access-token` or in
`PROTON_PASS_PERSONAL_ACCESS_TOKEN`. This uses the variable, because a
process's arguments are readable by every other process on the host: through
`/proc/<pid>/cmdline`, which is world readable on Linux, and through `ps`
anywhere. An argument would have disclosed the whole vault to every local
account for as long as the login took. An environment block is readable only
by the same user and by root.

</Accordion>

<Accordion title="The proxy cannot bind beyond loopback">

`ListenAddress` is a type that cannot represent a non-loopback address.
Anything other than `127.0.0.1`, `::1` or `localhost` is rejected when the
configuration loads - not at the first request.

The proxy performs no authentication of its own; it attaches a real credential
to whatever reaches it. Bound to `0.0.0.0` it would be an open
credential-lending service. Putting the rule in the type means a
misconfiguration cannot run at all, rather than running until someone notices.

To reach it from elsewhere, forward a port over SSH. The rule stays enforced and
access is authenticated by SSH rather than by nothing.

</Accordion>

<Accordion title="Resolved values are redacted by type">

A value is wrapped in Effect's `Redacted` from the moment it leaves `pass-cli`.
A `Redacted<string>` prints as `<redacted>` in logs, errors, stack traces and
`console.log`. Exactly three places unwrap it: the protocol response, the
child's environment, the outbound header.

An accidental log line elsewhere prints nothing.

</Accordion>

<Accordion title="Every executable logs to stderr">

stdout carries the resolver's protocol JSON and the proxy's forwarded payloads.
A log line on stdout would corrupt what the Gateway parses - and could, in
principle, interleave a diagnostic into a credential response. Tests spawn the
built binaries and assert stdout parses as JSON.

</Accordion>

<Accordion title="There is one failure reason, not two">

`NOT_FOUND` covers both "absent from the map" and "the vault holds nothing
there". Distinguishing them would let a caller use the provider to enumerate
which ids exist.

</Accordion>

<Accordion title="The proxy returns no detail on failure">

An unresolvable secret is a `502` with no explanation. The client asked for a
proxied call, not for the state of your vault.

</Accordion>

<Accordion title="Nothing is cached to disk">

There is no credential cache on disk and no fallback to a stale value. The
proxy memoises in memory for 30 minutes so a conversation does not cost a vault
round trip per message; that dies with the process and is invalidated by a
`401`.

</Accordion>

<Accordion title="Telemetry has no field a secret could occupy">

Not a filter - an absence. See [telemetry](/security/telemetry).

</Accordion>
</AccordionGroup>

## What it does not protect against

Being clear about this is more useful than a longer list of guarantees.

<Warning>
**Any process running as your user can ask for these secrets.** The vault is
unlocked for that account by design - that is the point of an agent token. This
narrows *where a credential is written down*; it does not sandbox what is
already running with your permissions.
</Warning>

- **A compromised agent token is a compromised vault.** It is scoped to one
  vault and it expires, which bounds the damage, but within that vault it is
  full read access. Give it its own vault, set an expiry, and revoke it if the
  machine is lost.
- **The consuming program can do what it likes with the value.** Once the MCP
  server or the model provider client has the credential, this system has no
  further say.
- **The map is not secret.** It reveals which services you hold credentials for
  and which vault items they live in.
- **`hostname` is reported by telemetry when it is on.** On a personal machine
  that often identifies a person. One variable turns it off.
- **A local privilege escalation defeats all of this.** So does a keylogger.
  Neither is in scope.
- **Anything that can set this process's environment can redirect it.**
  `PASS_CLI` names the binary that talks to the vault, and `PATH` decides
  which one is found when it is unset. Whoever controls either can substitute
  a program of their own and be handed the agent token. That is not a
  weakness that can be closed from inside the process: something that can
  rewrite your environment can already replace the binary itself. It does
  mean the environment a service runs with is part of the trust boundary,
  which is the argument for the generated unit, agent and task files rather
  than an ad-hoc shell wrapper.
- **The proxy attaches credentials for any local caller.** It performs no
  authentication of its own. It is bound to loopback and no further, but any
  process running as you can reach it, which is the same boundary as the
  first warning above rather than an additional one.

## Supply chain and code injection

The question this answers is whether someone can get code of their own into
the copy you run, and thereby reach the token.

<AccordionGroup>
<Accordion title="Nothing is loaded at runtime that was not in the build">

There is no `eval`, no `new Function`, and no dynamic `import()` or
`require()` anywhere in the sources. Nothing reads a plugin directory, and
none of the configuration files can name code: the secret map holds vault
references, the route file holds URLs and header names, and both are parsed
into branded types that cannot represent anything else.

Each published binary is a single self-contained bundle with no
`node_modules` beside it, so there is no directory an attacker can drop a
module into and have it resolved ahead of the real one.

</Accordion>

<Accordion title="Dependencies cannot run code when they are installed">

`pnpm-workspace.yaml` carries an `allowBuilds` allowlist, so a package may run
an install script only if it is named there. Four are: esbuild, nx,
`@parcel/watcher` and `msgpackr-extract`. Everything else in the tree is
denied by default, which is the usual route a compromised transitive
dependency takes.

A minimum release age is also enforced, so a version published minutes ago
cannot be pulled into a build before anyone has looked at it. `pnpm install`
reports whether the lockfile passes both.

</Accordion>

<Accordion title="The release pipeline is pinned and scoped">

Every GitHub Action is pinned to a commit SHA rather than a tag, because a
tag can be repointed at new code by whoever owns the action. CI declares
`contents: read` and nothing else. The publish job is the only one that holds
a registry token, and packages are published with npm provenance, so the
build that produced a release is attestable.

The version specifier a release is dispatched with reaches the shell as an
environment variable and is checked against a pattern first, so it cannot be
read as shell syntax on its way to a command that publishes.

</Accordion>

<Accordion title="What this does not answer">

A dependency that is compromised *before* its install script runs, in the
package's own code, still executes inside the process and can read the token.
Bundling and allowlisting shrink the surface; they do not remove it. The
mitigation there is the same one the whole design rests on: the token is
scoped to one vault, it expires, and every read it performs is recorded in
`pass-cli agent monitor`, so a compromise is bounded and visible rather than
silent and total.

</Accordion>
</AccordionGroup>
