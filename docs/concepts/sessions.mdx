## Why not your own session

The OpenClaw Gateway starts at boot. There is no terminal, nobody has signed
in, and there is no user session for it to borrow.

So it authenticates with a **Proton Pass agent token**: a credential scoped to
one vault, with an expiry, revocable on its own without touching your account.

```bash
pass-cli agent create openclaw-gateway --expiration 1y --vault OpenClaw
openclaw-proton-pass token   # paste the token, then Ctrl-D
```

The token is the one credential this system keeps, and it is the root of the
whole arrangement: anything that can read it can read that vault. It lives
either in a file readable only by your account, or in
`OPENCLAW_PROTONPASS_AGENT_TOKEN`, which takes precedence when both exist.
The two fail differently rather than one being safer; [the security
model](/security/model) sets out which suits which host.

It is never passed to `pass-cli` as a command-line argument, because a
process's arguments are readable by every other process on the host. It
travels in `PROTON_PASS_PERSONAL_ACCESS_TOKEN` instead.

## Every read is recorded, and says what it was for

Agent tokens refuse audited reads unless a reason is given, and that reason is
the only thing the audit log shows about *why* a credential was taken. A
constant string would satisfy the requirement and waste it: every entry would
look the same, so the log could prove that a read happened and nothing about
which one. So the reason is built from what the calling binary actually knows:

```
OpenClaw resolver reading OPENAI_API_KEY, DISCORD_BOT_TOKEN
OpenClaw mcp-auth-proxy reading CONTEXT7_MCP_AUTHORIZATION for route /context7
OpenClaw pass-run reading CONTEXT7_API_KEY for command context7-mcp
```

Read them back with:

```bash
pass-cli agent monitor openclaw-gateway
```

Only names travel. The ids are the keys of the secret map, which [the security
model](/security/model) already treats as non-secret, and the target is a
route path or a command name out of your own configuration. The resolved value
and the `pass://` reference it came from are both deliberately absent: Proton
knows which item it served without being told.

### Saying which agent or task asked

<Warning>
OpenClaw tells a secret provider nothing about the agent, session or task
behind a request. The exec protocol carries a protocol version, a provider
name and a list of ids, and the provider runs with a filtered environment.
There is no agent name to record, so this system does not invent one.
</Warning>

What it can do is carry something you supply. `OPENCLAW_PROTONPASS_AUDIT_LABEL`
is free text appended to every entry, and is the place for whatever this host
knows that the code cannot work out:

```bash
export OPENCLAW_PROTONPASS_AUDIT_LABEL='upstash box, nightly summariser'
```

```
OpenClaw resolver reading OPENAI_API_KEY (upstash box, nightly summariser)
```

`OPENCLAW_PROFILE` is also read, without being configured, because OpenClaw
sets it. A multi-profile install then distinguishes itself on its own:

```
OpenClaw resolver reading OPENAI_API_KEY (profile work)
```

Both are transmitted to Proton on every audited read and stored in the vault's
audit log, so they are for identification and not for anything confidential.
Entries are capped at 300 characters, which is Proton's limit; a longer one is
truncated so the binary and the first ids survive rather than the read being
refused.

That log is a genuine gain over a credential in a settings file. A file cannot
tell you who read it, let alone what for.

## Why a separate session directory

`pass-cli` keeps one session per directory. If this provider used the default,
the Gateway and your own terminal would take turns logging each other out.

So it sets its own:

```
PROTON_PASS_SESSION_DIR=~/.local/state/openclaw-protonpass
```

That directory belongs solely to this provider, which is what makes the repair
below safe.

## The three-step bootstrap

<Steps>
  <Step title="Reuse">
    Probe the existing session with `pass-cli info`. If it works, use it.

    The probe reads the **exit code**, not the output. `Command.string` resolves
    with whatever a process wrote to stdout even when it exited non-zero, so a
    probe built on output would report every broken session as healthy and the
    login path below would never run.
  </Step>
  <Step title="Log in">
    Log out, then log in with the agent token.

    The logout is not optional: `pass-cli login` refuses with "Already
    authenticated" whenever a session file exists - including a stale one that
    `info` can no longer read.
  </Step>
  <Step title="Rebuild">
    Delete the session directory and log in again.

    `pass-cli` keeps an encrypted database in the session directory whose key
    derives from the token. `logout` leaves that database behind, so once the
    token is rotated it can no longer be decrypted and every login fails with an
    opaque sqlcipher error. The directory belongs only to this provider, so
    rebuilding it is the correct repair rather than a workaround.
  </Step>
</Steps>

If all three fail, resolution fails with a `SessionError`. It does not retry
indefinitely and it does not fall back to anything.

<Note>
Which of the three paths was taken is reported as telemetry - `reused`,
`logged-in` or `rebuilt` - because a host that rebuilds on every call is a host
with a problem worth seeing. The three words are the whole payload; see
[telemetry](/security/telemetry).
</Note>

## Rotating the token

```bash
pass-cli agent create openclaw-gateway --expiration 1y --vault OpenClaw
openclaw-proton-pass token   # paste the token, then Ctrl-D
```

Nothing else is required. The next resolution finds the old session
undecryptable, rebuilds the directory, and logs in with the new token. That
path exists precisely because it was hit for real, not because it was imagined.
