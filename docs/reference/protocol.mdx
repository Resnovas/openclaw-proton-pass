---
title: "Resolver protocol"
description: "The JSON contract between the OpenClaw Gateway and openclaw-protonpass-resolver - one request on stdin, one response on stdout."
---

The Gateway starts the resolver, writes one JSON document to its stdin, reads
one JSON document from its stdout, and the process exits.

<Warning>
**stdout carries the protocol and nothing else.** Every component logs to
stderr, because one log line interleaved with the response corrupts what the
Gateway parses. This is pinned by tests that spawn the built binary and assert
its stdout parses as JSON.
</Warning>

## Request

```json
{
  "protocolVersion": 1,
  "provider": "protonpass",
  "ids": ["CONTEXT7_API_KEY", "ANOTHER_ID"]
}
```

<ResponseField name="protocolVersion" type="1" required>
  The only version implemented.
</ResponseField>

<ResponseField name="provider" type="string">
  Accepted but not checked. The Gateway only ever invokes the command it was
  configured with, so rejecting a name mismatch would fail correct
  configurations that simply named the provider something else.
</ResponseField>

<ResponseField name="ids" type="string[]" default="[]">
  The ids to resolve. An absent or empty list is valid and resolves nothing.
</ResponseField>

## Response

```json
{
  "protocolVersion": 1,
  "values": { "CONTEXT7_API_KEY": "..." },
  "errors": { "ANOTHER_ID": "NOT_FOUND" }
}
```

<ResponseField name="protocolVersion" type="1" required />

<ResponseField name="values" type="object">
  Resolved values, keyed by id, with any decoration from the secret map already
  applied.
</ResponseField>

<ResponseField name="errors" type="object">
  Per-id failures, keyed by id. The only value is `"NOT_FOUND"`.
</ResponseField>

<ResponseField name="error" type="string">
  Protocol-level failure: nothing could be produced at all.
</ResponseField>

### One reason, deliberately

`NOT_FOUND` covers both "absent from the map" and "the vault holds nothing
there". They are answered identically so the provider cannot be used to
enumerate which ids exist.

### Partial success is success

One unknown id must not deny the Gateway the others, so per-id failures travel
inside an otherwise successful response. `error` at the top level is different:
it means the map was unreadable, or no session could be established.

## Resolution in one vault call

Every requested reference is resolved in a **single** `pass-cli` invocation
rather than one per id:

```bash
pass-cli run --no-masking -- bash -c 'printf "%s\0" "$OPENCLAW_SECRET_0" ...'
```

`pass-cli run` substitutes any environment variable whose value is a `pass://`
URI, so one call covers the whole batch. Values are NUL-separated because a
credential may contain anything except a NUL byte.

<Accordion title="Why --no-masking">
The point of the call is to emit the values. That output is consumed in-process
and never reaches a terminal or a log; masking it would simply make the call
useless.
</Accordion>

<Accordion title="Why the exit code is read rather than the output">
`Command.string` resolves with whatever a process wrote to stdout even when it
exited non-zero. Built on that, a vault error would have become a silent batch
of empty values - every id reported `NOT_FOUND` with no indication that the
vault had failed. Both the session probe and resolution read the exit code.
</Accordion>

## Timeouts

A vault call is abandoned after `OPENCLAW_PROTONPASS_TIMEOUT_MS` (60s). Set
OpenClaw's `secrets.providers.protonpass.timeoutMs` to at least that, or the
Gateway will give up first and you will see a Gateway timeout instead of the
resolver's own error.

## Trying it by hand

```bash
echo '{"protocolVersion":1,"ids":["CONTEXT7_API_KEY"]}' | openclaw-protonpass-resolver
```

<Warning>
This prints the credential to your terminal.
</Warning>

To see the protocol without seeing a value, ask for an id that does not exist:

```bash
echo '{"protocolVersion":1,"ids":["NO_SUCH_ID"]}' | openclaw-protonpass-resolver
```

```json
{ "protocolVersion": 1, "errors": { "NO_SUCH_ID": "NOT_FOUND" } }
```

<Accordion title="Notes for AI agents">
When parsing a response, read exactly one line from stdout and parse it as
JSON. Diagnostics are on stderr and must not be merged into stdout before
parsing. A non-zero exit code accompanies a top-level `error`, but a response
is still written in that case, so read stdout before inspecting the code.

`values` and `errors` are both optional. Absent is not the same as empty: a
request with no ids returns neither.
</Accordion>
