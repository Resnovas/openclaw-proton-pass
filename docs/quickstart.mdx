---
title: "Quickstart"
description: "From nothing to a credential resolved out of a Proton Pass vault, in five steps."
---

This walks through the first path - a credential field resolved by the
provider. The examples use [Context7](https://github.com/upstash/context7),
which is free and open source and authenticates with an `Authorization: Bearer`
key, so every command below can be run as written.

<Steps>
  <Step title="Install the Proton Pass CLI">
    Everything here resolves secrets by calling `pass-cli`, so install it
    first. It runs on Linux, macOS and Windows.

    <Tabs>
      <Tab title="Linux and macOS">
        ```bash
        curl -fsSL https://proton.me/download/pass-cli/install.sh | bash
        pass-cli --version
        ```
      </Tab>
      <Tab title="Windows">
        ```powershell
        Invoke-WebRequest -Uri https://proton.me/download/pass-cli/install.ps1 -OutFile install.ps1
        .\install.ps1
        pass-cli.exe --version
        ```
      </Tab>
    </Tabs>
  </Step>

  <Step title="Install this">
    As an OpenClaw plugin, which registers the secret provider for you:

    ```bash
    openclaw plugins install clawhub:@resnovas/openclaw-proton-pass
    ```

    Or as standalone commands:

    ```bash
    npm install -g @resnovas/openclaw-proton-pass
    ```

    Either way, prepare the configuration directory:

    ```bash
    openclaw-proton-pass setup
    ```

    `setup` creates the configuration directory so that only your account can
    read it, seeds the two configuration files if they are absent, and writes
    whatever this host uses to keep the proxy running. It never overwrites a
    configuration file that already exists.

    | Host | Configuration directory |
    | --- | --- |
    | Linux and macOS | `~/.config/proton-pass-cli` |
    | Windows | `%APPDATA%\proton-pass-cli` |

    What it writes for the proxy differs by host: a systemd user unit, a
    launch agent, a Task Scheduler definition, or, where there is no init
    system at all, a launcher script. `setup` prints the path and the command
    that enables it. See [running it as a
    service](/guides/running-as-a-service).
  </Step>

  <Step title="Create the agent token">
    ```bash
    pass-cli agent create openclaw-gateway --expiration 1y --vault OpenClaw
    openclaw-proton-pass token
    ```

    `token` reads the token from standard input and writes it where the
    resolver looks for it, readable only by your account. Paste it and press
    `Ctrl-D` (`Ctrl-Z` then `Enter` in Command Prompt), or pipe it in:

    ```bash
    openclaw-proton-pass token < token.txt
    ```

    A dedicated agent token rather than your own session, because the Gateway
    starts at boot. Every read it performs is recorded:

    ```bash
    pass-cli agent monitor openclaw-gateway
    ```
  </Step>

  <Step title="Map an id to a vault location">
    Edit `~/.config/proton-pass-cli/openclaw-secret-map.json`:

    ```json
    {
      "CONTEXT7_API_KEY": "pass://OpenClaw/context7.com/API Key",
      "CONTEXT7_MCP_AUTHORIZATION": {
        "ref": "pass://OpenClaw/context7.com/API Key",
        "prefix": "Bearer "
      }
    }
    ```

    This is the only file that records where anything lives. Moving an item
    between vaults is an edit here, not a configuration migration.

    The second form exists because one vault entry has to serve both a bare
    credential field and an HTTP header that needs a scheme in front of the
    token - see [ids, references and values](/concepts/ids-references-values).
  </Step>

  <Step title="Register the provider">
    Installed as a plugin, this is already done: the manifest declares the
    provider and OpenClaw materialises it at startup.

    Configure it by hand only when running the binaries standalone:

    ```bash
    openclaw config set secrets.providers.protonpass.source exec
    openclaw config set secrets.providers.protonpass.command "$(command -v openclaw-protonpass-resolver)"
    openclaw config set secrets.providers.protonpass.jsonOnly true
    openclaw config set secrets.providers.protonpass.timeoutMs 60000
    ```

    Restart the Gateway afterwards.
  </Step>

  <Step title="Check it">
    ```bash
    openclaw-proton-pass doctor
    ```

    Read-only - it reports what is installed, configured and missing, and
    repairs nothing, so it is safe to run on a live host.

    To exercise the protocol directly:

    ```bash
    echo '{"protocolVersion":1,"ids":["CONTEXT7_API_KEY"]}' \
      | openclaw-protonpass-resolver
    ```

    <Warning>
    That prints the resolved value to your terminal, and therefore into your
    shell history if the shell records output. Use it to confirm the path
    works, then rotate the item if the terminal is not private.
    </Warning>
  </Step>
</Steps>

## Then point a field at it

```bash
openclaw config set models.providers.openai.apiKey \
  --ref-provider protonpass --ref-source exec --ref-id CONTEXT7_API_KEY
```

<Accordion title="Notes for AI agents">
Do not run the `openclaw-protonpass-resolver` verification command on a user's
behalf without saying that it prints the credential to the terminal. Prefer
`openclaw-proton-pass doctor`, which reports paths and outcomes only.

`setup` never overwrites an existing `openclaw-secret-map.json`. If a map
already exists, edit it; do not delete it to make `setup` reseed it.
</Accordion>
